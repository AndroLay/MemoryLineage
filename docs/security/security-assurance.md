# Bounded security assurance

MemoryLineage does not claim a formal verification result, a third-party audit,
or security certification. The repository now publishes a bounded executable
assurance report so a reviewer can inspect exactly which negative paths were
run against the Solidity trust anchor.

## Reproduce the report

```bash
cargo run -q -p ml-cli -- security bounded-audit
cargo xtask verify
```

The deterministic artifact is:

```text
evidence/local/security_assurance_report.json
```

The report is produced by `ml-local-evm` using `revm` against the checked-in
creation artifact:

```text
contracts/artifacts/memory_lineage_registry_creation.hex
```

The current bounded pass exercises:

- five valid sequential transitions whose Rust-derived roots are compared with
  the executed Solidity registry;
- six stale predecessor values, including the zero root, an unrelated root,
  and four earlier committed roots, all rejected with `BAD_PREVIOUS_STATE`;
- a sequence gap and a zero sequence, both rejected with `BAD_SEQUENCE`;
- the published 20-case mutation matrix;
- the ERC-1271 accept/reject boundary;
- authority rotation, nonce advancement, old-authority rejection, and new
  authority acceptance;
- an explicit assertion that the report exports no raw memory.

The gate checks that the report is regenerated byte-for-byte and that it has
the following status vocabulary:

```text
status       = BOUNDED_ASSURANCE_PASS
formal_status = NOT_FORMALLY_VERIFIED
```

## Threat model covered by this pass

The pass is aimed at contract-level lineage failures where a caller attempts to
submit a state that:

- skips or rewinds the required sequence;
- names a predecessor other than the registry head;
- reuses an old or malformed authorization;
- changes a commitment while retaining an old signature;
- uses the wrong EIP-712 chain or verifying-contract domain;
- uses a disabled contract authorizer; or
- continues with an old authority after rotation.

The report tests the behavior of this pinned implementation and corpus. It does
not model every EVM environment, compiler configuration, RPC behavior, key
management failure, denial of service, or off-chain storage failure.

## What remains unclaimed

The bounded report is not:

- a mathematical proof over all inputs;
- a formal Solidity verification result;
- a third-party smart-contract security audit;
- a penetration test;
- a statement that the registry or agent is secure in every deployment; or
- evidence that a production agent runtime has adopted the adapter.

The repository therefore keeps `formal security audit` and `external adoption`
as separate `NOT CLAIMED` / `NOT YET DEMONSTRATED` statuses. This is deliberate:
the executable evidence is stronger because its boundary is visible and
reproducible.

## Audit path for a future external reviewer

An independent auditor can start with the exact source and artifact, run
`cargo xtask verify`, inspect the generated JSON, and then review
`contracts/solidity/MemoryLineageRegistry.sol` against the listed invariants.
Any future external report should record the audited commit, compiler/artifact
hash, scope, findings, severity, and retest result before the website or
submission text is changed to mention an audit.
